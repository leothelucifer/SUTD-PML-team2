Sepsis Warning Pipeline

How the ICU data is split, how each candidate model is trained, how one model is chosen and frozen, how that model turns each patient hour into an alert, and how it would be deployed and maintained on AWS. Drawn from the code on main plus PR #48. Planned parts are marked as planned.

  1. 40,336 ICU stays
  2. 5 splits by stay
  3. 4 candidate models trained the same way
  4. 1 winner, frozen as a bundle
  5. Scored hour by hour, with a 6 h alert cooldown

1How the data is split

Each .psv file is one ICU stay. Whole stays go to one split, so hours from the same stay never appear on both sides. Hospital A is divided four ways, stratified so each part has the same septic share. Hospital B is kept whole as the external test, because the project's question is whether the model still works at another hospital.

2How each model is trained

Every candidate goes through the same six stages on the same splits. The coloured blocks show which split each stage learns from. Features are built from each stay's own past and current hours only, so nothing from a later hour can leak into an earlier score.

3How one model is chosen and frozen

After every candidate has a validation row, one rule picks the winner. The winner, its feature list and its threshold are saved together as one bundle. From that point nothing changes, and only then are the two test splits scored.

Recommended change to how choices are made

As planned, validation decides everything: model, feature set, settings and threshold. Every one of those decisions fits a little to the same ~269 septic stays. The fix moves the first three decisions into cross-validation inside train.

4How the final system runs

Each hour, the frozen model turns the patient's history so far into a probability. Two separate things then happen. Every hour above the threshold counts as a positive decision; this is what the PhysioNet utility scores. A visible alert is raised only if none was raised in the previous 6 hours, so staff are not paged every hour.

What makes this production-ready

  • Training, replay and the API share one feature module.
  • The bundle stores a versioned feature list and a checksum.
  • Scoring refuses a bundle whose feature list does not match.
  • Test splits only take a frozen, registered bundle.
  • No retraining happens automatically from a monitoring alert.

Limits to say out loud

  • Scores estimate the challenge label, not a diagnosis.
  • Probabilities calibrated at A (8.8% septic) will run high at B (5.7%).
  • The 0.2 false alerts per day budget is a demo choice, not a clinical one.
  • Stays, not people, are kept apart across splits.

5How the ICU calls the model

ICU devices never call the model directly. Readings are charted into the hospital record (EHR) as they happen. Once an hour, the hospital's integration engine collects each ICU stay's last 7 hourly rows and sends them over the VPN to the scoring service. The service adds what it remembers about that stay, scores the hour and replies. The hospital shows any alert to the care team.

How the service knows the earlier hours

Sending only the last 6 hours is not enough on its own. Several features look further back: Lactate__last and Lactate__hours_since_seen need the last lactate even if it was taken 20 hours ago, the HMM state depends on the whole stay, and the cooldown needs the last alert hour. So each call carries the last 7 raw hourly rows, and the service keeps a small state record per stay in DynamoDB. It holds, for every variable, the last value and the hour it was seen before those rows, plus the HMM forward state and the last alert hour. The model code itself keeps nothing between calls, and the hospital stores nothing extra.

  • A parity test: for every hour of every synthetic stay, 7 rows + state must give the same features as the full history.
  • An input schema for the 34 variables, with the same names and units as the .psv files (L02).
  • top_features from SHAP with a training-split background (M03).
  • A short mapping document for the hospital engine: codes and units to PhysioNet variables, and the hourly binning rule.

6Deploying on AWS and running MLOps

This section shows the long-term direction for tasks L01–L06. Nothing is provisioned. The diagram is a target architecture, not the current implementation plan; the first CloudFormation phase is intentionally smaller.

Initial CloudFormation scope: a public Application Load Balancer forwards to ECS Fargate tasks in private subnets, with encrypted artifact/state resources and basic alarms. It has no API Gateway, VPN, or authentication. Until authentication and other release gates are implemented, any deployed endpoint is for synthetic research traffic only.

How a model gets from code to production

Code and models are versioned separately. The Docker image is tagged with the git commit; the model is an MLflow version. The service is configured with one of each, so either can be rolled back on its own. Two human checks sit in the loop: before a model is approved and before it goes to production. Nothing retrains or redeploys automatically.

Build order for leo's tasks

  • L01: MLflow locally first; log one real training run with data and split hashes.
  • L02: FastAPI with the request and response from section 5, the DynamoDB state, OAuth2, and the parity test.
  • L03: Docker image, non-root user, no data or model inside the image.
  • L04: GitHub Actions running the tests and the 23 s synthetic demo on every PR.
  • L05: latency at p50, p95 and p99 for 7-row and full-history requests.
  • L06: modular CloudFormation for the first public-ALB/private-Fargate phase; lint only until deployment is approved.

Before anything goes to AWS

  • Owner approval for every resource and upload.
  • The initial API is public and unauthenticated: synthetic requests only; add authentication before non-synthetic use.
  • Use HTTPS and a narrow source CIDR before any deployment; configure a budget alert and review retained resources before teardown.
  • Slides label the cloud part as a design unless it was actually run.
